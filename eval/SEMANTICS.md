# 의미 보존 평가 설계

질문: 플러그인이 의사코드에 적용한 편집이 **코드가 하는 일을 바꾸지 않았는가**.
기준은 원본 C 소스가 아니라 **Fission이 낸 의사코드 그대로**다. Fission 출력 자체가 틀린 경우(`m0/README.md`)
후처리는 그 오류를 고치지도 악화시키지도 않아야 한다.

## 계층

| 층 | 검사 | 보장하는 것 | 상태 |
|---|---|---|---|
| L0 구조 | 적용기가 식별자 토큰만 치환, 충돌·키워드·미보고 변수 거부, 역 rename하면 원문과 바이트 동일 | 이름·주석 편집은 구조적으로 알파 동치 | `tests/test_apply.py` |
| L1 컴파일 오라클 | 편집 전후를 같은 컴파일러로 컴파일해 **어셈블리가 같은지** 비교 (`src/fission_plugins/oracle.py`) | L0이 실제 코드에서 맞게 동작했다는 독립 증거. 같다면 이 컴파일러·타깃에서 동작이 같음 | 이 문서의 측정 |
| L2 민감도 | 일부러 의미를 바꾼 변형을 주고 오라클이 잡는지 | 오라클이 눈먼 검사가 아님 | 이 문서의 측정 |
| L3 재작성(미구현) | 모델이 코드를 바꾸는 미래 기능용: 어셈블리 동일 → 아니면 순수 함수에 한해 차분 실행 → 아니면 거부 | 의사코드와의 동치만 주장 | 설계만 |

모델이 편집 목록만 내므로 v0는 L0만으로 의미 보존이 구조적으로 성립한다. L1은 그 주장을 실제 Fission
출력 위에서 확인하는 회귀 검사이고, 적용기나 정규식이 바뀔 때마다 돌린다.

## L1 오라클

Fission 의사코드는 그대로는 C가 아니다(`undefined8` 같은 Ghidra형 이름, 선언 없는 프로젝트 타입과 전역).
고정 전처리부(`stdint`, `stdbool`, Fission 타입 별칭)를 붙이고, clang이 모른다고 보고한 타입은 `long long`,
선언 없는 식별자는 `extern long long`으로 **그 함수에 한해** 보강한다. 편집 후 코드는 편집 전과 **같은 보강**으로
컴파일하므로 차이는 편집에서만 올 수 있다. 옵션: `-std=gnu89 -O1 -g0 -S`, 대상 `arm64-apple-macos`.

`-O1` 어셈블리는 지역 변수 이름이 남지 않으므로 지역 변수 rename과 주석은 어셈블리를 바꾸지 않는다.
함수 이름을 바꾸면 심볼과 컴파일러가 만든 지역 심볼(`l_switch.table.<함수>`)이 바뀌므로 비교 전에
새 이름을 옛 이름으로 되돌리고 `;` 주석을 지운다. 판정은 네 가지: `identical`, `different`,
`baseline_uncompilable`(검사 불가, 계수에서 제외하고 비율 보고), `edited_uncompilable`(편집이 코드를 깨뜨림).

한계: `identical`은 증명이고 `different`는 조사 신호다(충분조건이지 필요조건이 아님). 컴파일러 버전·타깃에 묶인다.
컴파일 안 되는 함수(아래 측정에서 6%)는 L0만 적용된다. 문자열 리터럴과 주석 안의 이름은 편집 대상이 아니라서
이 검사로 확인되지 않는다. 오라클은 동작의 동치를 보지, 이름이 **좋은지**는 보지 않는다.

## 측정 (2026-11-09, `eval/results/semantic-check-v1.json`, 시드 11)

6개 빌드(capstone arm64 O0/O1, isl arm64 O0/O1, isl x86-64 O0/O1)에서 빌드당 무작위 100개, 총 600개.
재현: `python3 eval/semantic_check.py <matrix-dir> <새 보고서 경로> --per-build 100 --seed 11`
(clang 경로는 `CLANG` 환경변수 또는 `/opt/homebrew/opt/llvm/bin/clang`).

| 항목 | 결과 |
|---|---|
| 컴파일 가능(보강 포함) | 564 / 600 (94%); 빌드별 87~100 |
| 정답(DWARF) 이름으로 모두 바꾼 편집 | 518 / 518 **어셈블리 동일** (적용된 rename 1,380개, 적용기 거부 2개) |
| 함수 이름 변경 | 564 / 564 동일 |
| 주석 추가 | 564 / 564 동일 |
| 상수 하나를 +1로 바꾼 변형 | 336 / 388 변경 감지(87%), 2개는 컴파일 불가, 50개는 동일 |
| 두 변수를 합친 변형(적용기 우회) | 300 / 489 감지(61%: 변경 244 + 컴파일 불가 56), 189개는 동일 |

해석:
- 기대한 불변식(rename·주석은 어셈블리를 바꾸지 않는다)은 600개 표본의 모든 컴파일 가능 함수에서 성립했다.
- 변형이 동일로 남는 경우는 대개 동작이 실제로 같은 변형이다(예: `local_8 = param_1` 복사 변수를 원 변수로 합침,
  실행되지 않는 코드의 상수). 따라서 오라클의 민감도는 상수 변경 87%, 변수 합침 61%이며, 이 값은 "편집이 동작을
  바꿨을 때 놓치는 비율"의 상한 추정이 아니라 변형 선택의 영향을 받는 참고치다. rename 전용 편집에서는 놓칠 것이
  없으므로(알파 동치) 민감도보다 위의 100% 성립이 핵심이다.
- 정답 이름을 모두 적용해도 거부가 거의 없다: 전체 코퍼스에서 제안 91,808개 중 80개(0.09%)가 거부됨
  (중복 이름 77, 기존 식별자와 충돌 3). 적용기는 병목이 아니다.
- 이 숫자는 두 프로젝트, 한 컴파일러(Homebrew clang), 한 대상에서의 값이다. Windows/ELF/PE 의사코드와
  다른 Fission 버전은 측정하지 않았다.

## 평가 파이프라인에서의 사용 (M2 이후)

모델 평가 때 예측 편집마다 `apply_edits` → `compare`를 돌려 (a) `identical` 비율, (b) `edited_uncompilable`
비율, (c) 적용기 거부 사유별 비율을 보고한다. (a)가 100% 미만이면 모델 문제가 아니라 적용기 버그이므로
릴리스를 막는다. 기본 이름 지표(정확도, 적용 범위-정밀도 곡선)는 `docs/PLAN_M2.md` 5절.

## L3 설계 메모 (모델이 코드를 바꾸게 될 때)

재작성은 기본 꺼짐. 켜려면 (1) 어셈블리 동일이면 통과, (2) 아니면 입력·출력이 모두 스칼라인 순수 함수에 한해
무작위 입력으로 차분 실행(forge의 Wasm 함수 평가기와 같은 방식, 시간·연료 제한), (3) 둘 다 불가능하면 거부.
통과해도 주장은 "의사코드와 같은 동작"까지다. 원본 소스와의 동치는 주장하지 않는다.
