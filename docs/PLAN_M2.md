## 1. 추출 방식: 이미 쓰는 구성을 확정한다

| 대상 | 방식 | 이유 |
|---|---|---|
| 어셈블리 | `llvm-objdump` (빌드 도구, 주소 범위로 자름) | 바이너리 전체 44만 줄이 1.3초. `fission_cli disasm`은 호출마다 바이너리 전체를 재분석(isl에서 약 7.5초) |
| 의사코드·변수표 | `fission_cli decomp --all --json`을 **바이너리당 1회** | 같은 이유로 함수별 호출 금지 |
| 정답 이름 | DWARF(`dwarfdump`) + 위치 기반 정렬 | 디컴파일러에 의존하지 않는 라벨 |
| P-code | v0에서 쓰지 않음 | 함수당 호출 비용. 코퍼스는 균등 표본 100개만 보관 |

**v0 모델 입력은 Fission 의사코드 + 변수표만으로 한다. 어셈블리는 코퍼스에 남기되 입력에서 뺀다.**
근거는 하나뿐이다: 학습 전 Qwen3.5-2B-Base 3-shot에서 의사코드 11.5%, 의사코드+어셈블리 10.7%(1004개 타깃,
차이는 표본 변동 안, `eval/README.md`). 이는 어셈블리를 본 적 없는 모델에 대한 결과라서 파인튜닝 후에는
달라질 수 있다. 그래서 어셈블리 유무는 M2 첫 학습 뒤 한 번 비교한다(7절).

알려진 한계(코퍼스 README 참조): x86-64 스택 변수는 정렬되지 않는다(isl O0 유일 라벨 17,597 대 arm64 27,968).
O1/O2는 같은 레지스터를 여러 원본 변수가 공유해 라벨이 모호하다. 어셈블리 범위가 Fission의 `disasm --function`과
어긋나는 함수가 capstone arm64 O1에서 3/160.

**라벨 사용 규칙(결정):** 학습 손실은 `unique`로 정렬된 변수에만 건다. `shared`, `none`, `multi-candidate`
변수는 정답을 모르므로 **손실에서 제외**하고, 출력에서는 건드리지 않는다. 모델이 "이름을 붙이지 않음"을 낼 수
있어야 하므로 편집 목록에 항목이 없으면 그대로 두는 계약을 유지한다(`schemas/edit-list.schema.json`).

## 2. 코퍼스의 실제 크기 (측정함)

| 항목 | 값 |
|---|---|
| 레코드(함수 × 빌드) | 37,200 (capstone 1,023 + isl 36,177, 6개 빌드: arm64/x86-64 × O0/O1/O2) |
| 서로 다른 (프로젝트, 함수 이름) | **8,402** (isl 8,210 + capstone 192) |
| `unique` 정렬 변수(빌드 합산) | 99,336 (isl 97,027 + capstone 2,309; 같은 원본 변수를 빌드마다 센 값) |
| 원본 소스를 자른 함수 비율 | isl 약 67%, capstone 약 93% |
| 의사코드 길이(Qwen3.5 토큰, arm64 O0/O1 450개 표본) | 중앙값 306, p90 1,404, p99 6,535 |
| 2,048 토큰 이하 비율 | 94% |

핵심: **독립 표본은 레코드 수가 아니라 서로 다른 함수 수(약 8천)이고, 프로젝트는 사실상 2개다.**
같은 함수는 빌드마다 코드는 다르지만 정답 이름이 같다. 그래서 분할은 반드시 함수 단위 이상(최종은 프로젝트 단위)
으로 하고, 같은 함수의 모든 빌드를 한 쪽에 넣는다.

## 3. 베이스 모델 후보와 선택 방법

`docs/MODEL_SELECTION.md`의 조사를 바탕으로, **빠른 길을 기준**으로 재정렬한다. 아키텍처 위험이 없는 모델을
기준선으로 두고, 신형은 변환 게이트를 통과해야만 학습에 쓴다.

| 순위 | 모델 | 역할 | 비고 |
|---|---|---|---|
| A | Qwen2.5-Coder-1.5B (또는 0.5B) | 안전한 기준선 | 일반 트랜스포머. llama.cpp 지원이 오래됨. 라이선스는 카드에서 재확인(기억: Apache-2.0) |
| B | Qwen3.5-2B-Base | 주 후보 | 하이브리드(Gated DeltaNet + Attention). 공식 SAE가 있으나 **선택 기준이 아니다** |
| C | Qwen3.5-0.8B-Base | 속도 계층 | B와 같은 파이프라인 |

선택 방법은 의견이 아니라 **같은 데이터·같은 프로토콜로 학습해 비교**하는 것이다(7절 M2a).
판정 기준: 양자화(Q4_K_M) 뒤 이름 정확도, 편집 적용 거부율, 함수당 지연, 최대 메모리.

**게이트 G1 (학습 비용을 쓰기 전에):** 후보마다 (1) HF → GGUF 변환, (2) Q4_K_M 양자화, (3) `llama-server`로
고정 프롬프트에 대한 생성이 되는지 확인한다. 하이브리드 구조는 이 경로가 검증되지 않았다(측정 안 함).
로컬에는 `llama-quantize`, `llama-server`가 있으나 변환 스크립트 `convert_hf_to_gguf.py`는 없다. 해당 버전의
llama.cpp 소스에서 받아야 하며, 받기 전에 확인을 구한다. 통과 못 하면 그 모델은 후보에서 뺀다.

크기 가늠(추정, Q4_K_M 약 0.6~0.7바이트/파라미터): 0.5B 약 0.4GB, 1.5B 약 1GB, 2B 약 1.4GB.

## 4. 학습 데이터 규모 (결정)

학습 가능한 양은 프로젝트 수가 정한다. 단계로 나눈다.

**D0 (지금 가능, 파이프라인 검증용):** isl + capstone 8.4천 함수. 프로젝트 단위 분할이 불가능하므로
isl 안에서 함수 단위로 나누고 capstone 전체를 보조 시험 세트로 둔다. **이 세트의 점수는 일반화 근거로
쓰지 않는다**(같은 프로젝트의 이름 관습이 학습에 섞임).

**D1 (주장을 하려면 필요):**
- 허용 라이선스 C 프로젝트 **10개 이상**, 서로 다른 함수 **약 3만 개 이상**, 프로젝트 **3개 이상을 학습 전에
  고정해 보류**(시험 전용). 3만이라는 수는 근거가 약한 목표치다(기억: 선행 연구들은 수십만~수백만 함수를 쓰지만
  대부분 처음부터 학습하거나 더 큰 모델이다). 그래서 아래 학습 곡선으로 조정한다.
- 후보 프로젝트(기억, 라이선스와 빌드 가능성 **미확인**): zlib, bzip2, lz4, zstd, sqlite, lua, cJSON, libpng,
  expat, libyaml, jansson, pcre2, mbedtls(Apache 선택). 로컬 `Fission/vendor`에는 학습에 쓸 만한 허용 라이선스 C
  프로젝트가 capstone과 isl 말고 없다(qemu, gcc, ProcessHacker 등은 GPL 계열이라 별도 결정 필요).
  소스를 내려받아야 하므로 시작 전에 확인을 구한다. 가중치 배포 가능 여부(`train_ok`)는 유지보수자가 정한다.

**학습 곡선으로 규모를 정한다 (M2a의 일부):** 같은 시험 세트에서 학습 함수를 1천 / 3천 / 9천으로 늘리며 정확도를
본다. 9천에서도 계속 오르면 D1 목표를 올리고, 포화하면 프로젝트 다양성이 병목이라는 뜻이다.

**계산량(추정, 첫 실행에서 실측으로 교체):** 예시당 평균 약 700토큰(중앙값 306, p90 1,404 사이에서 가정),
함수당 빌드 2개 사용, 3만 함수 → 6만 예시 × 700 = 약 4천만 토큰/에폭. L4 LoRA를 초당 3천 토큰으로 가정하면
약 4시간/에폭, A100은 그 1/3 정도. 2,048토큰 초과 함수(6%)는 v0에서 제외하고 건너뛴 비율을 기록한다.

## 5. 평가 지표 (DESIGN.md 8절에 추가)

1. 이름 정확도: 정확 일치, 정규화 일치, 서브토큰 F1. 기준선은 무변경, 타입 기반 규칙, 학습 전 3-shot.
2. **함수 이름 가림 변형:** 보고 지표는 의사코드 안의 함수 이름을 가린 입력도 함께 낸다. 지금은 `strip -S`가
   내보낸 심볼을 지우지 않아 함수 이름이 힌트로 남는데(`eval/README.md`), 숨겨진 함수에서는 없다.
3. **적용 범위-정밀도 곡선:** 모델이 확신하는 이름만 적용하는 임계값을 바꿔 가며 (적용한 변수 비율, 그중 정답
   비율)을 낸다. 틀린 이름이 `param_1`보다 나쁠 수 있으므로 단일 정확도 숫자로 평가하지 않는다.
4. 의미 보존: `eval/SEMANTICS.md`의 컴파일 오라클. 항상 100%여야 하는 불변식이다.
5. 양자화 손실, 지연, 최대 메모리. 시드·모델 리비전·데이터 해시 기록.
6. 시드 변동: forge 실험에서 같은 설정이 시드만 바꿔 0~53점 흔들렸다. 파인튜닝은 덜하겠지만 모델 비교는
   **시드 2개 이상 또는 함수 단위 부트스트랩 신뢰구간**으로 한다. 단일 시드 결과는 그렇다고 표기한다.

## 6. 하지 않을 것

처음부터 학습하는 모델(forge 쪽 결론은 `fission-forge` 증거 폴더), 코드 전체 재작성(편집 목록 계약 위반),
타입 변경 적용(v0는 보고만).

## 7. 실행 순서와 게이트

1. **G1:** 후보 3개의 GGUF 변환·양자화·생성 확인(위 3절). 변환 스크립트를 받기 전 확인.
2. **D0 학습 세트 만들기:** `eval/prepare_names.py`를 편집 목록 형식(입력 = 의사코드 + 변수표, 출력 = 편집 목록
   JSON, 손실은 출력에만)으로 확장하고 함수 단위 분할·해시·매니페스트 기록.
3. **M2a:** 후보 3개 × 학습 함수 1천/3천/9천, Colab(L4는 LoRA, A100은 전체 파인튜닝 가능), 완성부 손실만,
   검증 손실로 체크포인트 선택, 시험 세트는 마지막에 한 번. 산출: 정확도 대 데이터 곡선, 양자화 손실, 어셈블리
   입력 유무 비교 1회.
4. 결과를 보고 D1(프로젝트 추가 수집)의 목표를 정하고, 모델 하나로 압축.
5. M1(호스트 CLI)은 모델과 독립이므로 병행 가능. 규칙 기반 플러그인으로 end-to-end를 먼저 돌린다.
