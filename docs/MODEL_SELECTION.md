# 베이스 모델 후보 조사 (2026-10-29)

방법: `huggingface_hub` Python API(설치된 `hf` CLI 1.2.3에는 검색 명령이 없음)로 공식 조직의 최근 소형 모델을 조회하고,
후보의 `config.json`과 모델 카드를 읽었다. **가중치는 내려받지 않았다.** 아래 숫자는 각 카드에 적힌 값이며,
벤더마다 평가 조건이 달라 서로 비교할 수 없다. 결정은 M0/M2에서 같은 데이터로 직접 재서 한다.

코드 전용 소형 모델의 최신 계보는 찾지 못했다. Qwen3-Coder는 30B 이상(`Qwen3-Coder-30B-A3B`, `-Next`)이고
소형 코드 전용은 Qwen2.5-Coder(2024)가 마지막이다. Qwen3.5 카드(베이스/instruct)에서 코드 벤치마크 행은 찾지 못했다.
Granite 카드에는 HumanEval/MBPP 표가 있으나 열 라벨을 파싱하지 못해 인용하지 않는다.

## 내부 뉴런: Qwen-Scope SAE

`Qwen/SAE-Res-Qwen3.5-2B-Base-W32K-L0_50` (논문 arXiv:2605.11887, 2026-05 갱신): Qwen3.5-2B-Base의 **잔차 스트림에 대한
TopK 희소 오토인코더**, 0~23층 전부, 층마다 `d_sae=32768`(16배), `k=50`, 파일 `layer{n}.sae.pt`(`W_enc`/`W_dec`/`b_enc`/`b_dec`).
카드에 `transformers` 훅으로 특징 활성값을 뽑는 예제가 있다. 같은 계열 SAE가 9B, 27B, 35B-A3B에도 있다.
SAE 라이선스는 `license: other`(이름 `qwen`)로 모델의 Apache-2.0과 **다르므로** 사용 전에 LICENSE 본문을 읽어야 한다.

이것으로 할 수 있는 일(제안, 아직 안 함):
1. 의사코드 `param_1`, `x0`, `w8`, `xVar15` 같은 토큰에서 어떤 특징이 켜지는지 보고, 파인튜닝 전후로 "변수 역할(버퍼, 길이, 해시, 인덱스)"
   특징이 어느 층에서 생기는지 비교한다.
2. rename 실패 사례(잘못된 이름)와 성공 사례의 특징 활성을 비교해 오류 원인을 가설로 만든다.
3. 파인튜닝이 베이스의 특징 사전을 얼마나 바꿨는지 확인한다(카드는 베이스 SAE를 post-training 체크포인트에 적용하는 것도 "대체로 합리적"이라고 적음).

한계: 하이브리드 구조(Gated DeltaNet)에서 잔차 스트림 SAE가 선형 어텐션 층 정보를 얼마나 잘 설명하는지는 이 조사로 알 수 없다.
SAE 특징의 해석은 사후 라벨링이라 인과 검증(특징 제거/주입 실험) 없이는 가설일 뿐이다.

## 잠정 권고

1. **주 후보: Qwen3.5-2B-Base** — Apache-2.0, 로컬 llama.cpp가 아키텍처를 알고, 공식 SAE로 내부 분석이 가능한 유일한 후보.
2. **속도 계층: Qwen3.5-0.8B-Base** — 같은 계열이라 파이프라인을 공유한다.
3. **기준선: Qwen2.5-Coder-0.5B** — 합성 문법에서 이미 측정된 값이 있어 회귀 비교용.
4. 보류: Gemma 4 E2B(유효 크기 대비 메모리가 큼), Granite 4.1 3B(크지만 구조가 단순해 대안), LFM3(로컬 llama.cpp 미지원, 라이선스 비표준).

## 확인되지 않은 위험

- 하이브리드 선형 어텐션 모델을 파인튜닝한 뒤 GGUF로 변환·양자화(Q4/Q8)하고 llama.cpp에서 돌렸을 때의 정확도·속도는 **미검증**.
  아키텍처 문자열이 있다는 것만 확인했다.
- 2B 전체 파인튜닝은 Colab L4(24GB)에서 메모리가 빠듯하다(가중치+AdamW만 대략 수십 GB로 추정). L4에서는 LoRA, A100에서는 전체 파인튜닝이 현실적이다. 계산은 추정이다.
- Qwen3.5는 비전 인코더가 붙은 멀티모달 체크포인트다. 텍스트 전용으로 로드해 파라미터를 줄일 수 있는지는 미확인.
- 위 표의 날짜·다운로드 수는 조회 시점 값이다.
