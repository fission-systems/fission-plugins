python3 training/audit_dataset.py <출력 폴더>                       # audit.json, nearest_train_jaccard.json
```

기본값은 arm64, O0/O1/O2, 시드 20261110. 기존 폴더는 덮어쓰지 않는다. 지금 만든 세트는
`/Users/sjkim1127/fission-plugins-corpus/d0-v1`(38MB, 리포 밖)에 있고 입력 코퍼스(`matrix2`)와 각 파일의 sha256이
`manifest.json`에 있다.

## 예시 형식

한 줄이 JSON 한 개(`<split>.jsonl`). **학습 손실은 `completion`에만 건다.** `prompt` 끝은 줄바꿈이다.

```
prompt:      Fission pseudocode:
             ```c
             <의사코드>
             ```
             Variables:
             - param_1: long long (arg 0)
             - local_c: int (stack)
             Restore the source names for: param_1
             Edit list (JSON):
completion:  {"renames": {"param_1": "list"}}
```

그 밖의 필드: `id`, `split`, `group`, `project`, `license`, `arch`, `opt`, `address`, `name`, `targets`,
`function_name_masked`, `n_tokens`(토크나이저별 프롬프트+정답 토큰 수).

**타깃(정답을 요구하는 변수)은 DWARF와 `unique`로 정렬된 변수뿐이다.** `shared`/`none`/`multi-candidate`
변수는 정답이 없으므로 프롬프트의 변수표에는 나오지만 타깃에는 넣지 않아 손실이 걸리지 않는다. 모델은 요청받은
변수만 답한다. 따라서 **모델이 "이름을 붙이지 않음"을 학습하지는 않으며**, 추론 시 어떤 변수를 요청할지와 확신이
낮은 답을 버리는 규칙은 호스트의 몫이다(PLAN_M2 5절의 범위-정밀도 곡선). 모든 정답 편집은 `apply_edits`로 검사해
적용기가 거부할 항목(중복 새 이름 등)을 뺐다.

함수 이름 가림: 학습 예시의 약 50%는 의사코드 안의 자기 함수 이름을 `FUN_<주소 8자리>`로 바꿨다(함수 단위로 결정).
평가 분할(`val`, `test`, `xproj`)은 가리지 않은 파일과 가린 파일(`*-masked.jsonl`)을 따로 둔다. `FUN_<주소>`가
Fission이 숨은 함수에 쓰는 실제 이름과 같은지는 확인하지 않았다(가정). 호출하는 다른 함수 이름은 가리지 않는다.

## 분할

함수 단위가 아니라 **그룹 단위**다. 식별자와 숫자를 지운 토큰 모양이 같은 함수(`isl_*_list_*` 같은 템플릿
복제)는 모든 빌드에서 한 그룹이고, 그룹은 통째로 한 분할에 간다. 그룹 크기가 100을 넘으면 학습으로 보낸다
(가장 큰 그룹이 1,638개 함수). capstone은 학습하지 않는 `xproj`(다른 프로젝트) 시험 세트다.

| 분할 | 예시 | 함수 | 그룹 | 타깃 변수 |
|---|---:|---:|---:|---:|
| train | 11,568 | 6,669 | 3,240 | 31,654 |
| val (가림 없음 / 가림) | 1,220 / 1,219 | 715 | 420 | 4,086 |
| test (가림 없음 / 가림) | 1,081 / 1,079 | 635 | 416 | 3,429 |
| xproj, capstone (가림 없음 / 가림) | 356 / 356 | 166 | 125 | 925 |

학습 토큰은 Qwen3.5 토크나이저로 743만(예시당 평균 643), Qwen2.5-Coder로 680만(평균 588). 프롬프트와 정답을 합쳐
**2,048토큰을 넘는 예시는 뺐다**(2,501개, 만든 예시의 약 13%). 긴 함수가 학습과 평가에서 빠졌으므로 결과는 짧은
함수 쪽으로 편향된다. 같은 함수의 빌드 간 동일 프롬프트 1,684개는 중복으로 제거했다.

## 감사 결과 (`audit.json`)

- 분할 사이 **그룹, 함수 이름, 정확히 같은 토큰 모양의 겹침은 val/test에서 0**이다.
- 그러나 근사 복제는 남는다. 토큰 4-gram Jaccard로 가장 비슷한 학습 함수를 찾으면 val/test 함수의 **13~15%가
  0.8 이상**이고 중앙값은 0.5다(xproj는 중앙값 0.31, 0.8 이상 3%). 예시별 값은 `nearest_train_jaccard.json`에 있어
  평가 때 유사도 구간별로 나눠 보고할 수 있다(isl 평가 행 2,301개 중 1,015개가 0.5 미만).
- **정답 이름 어휘가 거의 닫혀 있다.** val/test 정답 이름의 97~98%가 학습 정답에 이미 나오고, 상위 20개 이름(`i`,
  `space`, `list`, `user`, `ctx`, `n`, …)이 정답의 43~48%를 차지한다. capstone(xproj)은 35%만 학습에 나온다.

## 이 세트로 말할 수 있는 것과 없는 것

- isl 안의 val/test 점수는 **같은 프로젝트의 이름 관습과 근사 복제 덕에 낙관적**이다. 파이프라인이 맞게 학습되는지,
  학습 곡선이 어떤 모양인지 보는 용도다. 일반화 주장에는 쓰지 않는다.
- 프로젝트가 달라지는 신호는 xproj뿐이고 규모가 작다(함수 166개, 그룹 125개, 타깃 925개).
- 레이블은 arm64 정렬 규칙(손으로 87쌍 확인, 85 정확 / 2 부분 정확)에 기대고 x86-64는 포함하지 않았다
  (`--archs arm64,x86_64`로 추가 가능, 정렬 검증 전). O1/O2는 `unique` 변수만 남아 레지스터 변수가 적다.
- 정답은 "원본 소스 이름"이지 "좋은 이름"이 아니다.

## 학습: `finetune.py` (M2a)

```bash
python3 training/finetune.py --model Qwen/Qwen2.5-Coder-1.5B --data <d0 폴더> --out <새 폴더> --functions 3000 --seed 1
```

transformers + peft만 쓰는 LoRA 학습이다(r=16, alpha=32, 모든 선형층, lr 2e-4 코사인, 2에폭, AdamW).
`pip install peft`가 필요하다. 후보 모델 3개를 같은 데이터와 같은 값으로 돌리려고 모델 이름만 바꾸게 했다.

- **손실은 정답(completion)과 EOS에만** 건다. 프롬프트 라벨은 -100. 최적화 한 번마다 합산 손실을 그 묶음의
  정답 토큰 수로 나눈다(시퀀스 수가 아니다).
- **학습 함수 수 곡선:** `--functions N`은 시드 고정 순서(`--subset-seed`)의 앞 N개 함수다. 1천 ⊂ 3천 ⊂ 전체
  (중첩)이고, 고른 함수의 모든 빌드·가림 변형을 함께 쓴다. **D0 학습 분할은 6,669개 함수뿐이라 PLAN_M2의 9천은
  나오지 않는다.** 곡선은 1천 / 3천 / 6.7천(전체)이고, 9천 이상은 D1(프로젝트 추가)이 있어야 한다.
- 검증 손실을 `--eval-every` 단계마다 고정 부분집합(`--val-examples`, 기본 함수 600개의 가림·가리지 않음)에서
  재고 가장 낮은 어댑터를 `<out>/best`, 마지막을 `<out>/final`에 저장한다. 시험 세트는 이 스크립트가 읽지 않는다.
  손실이 가장 낮은 체크포인트와 이름 정확도가 가장 높은 체크포인트가 다를 수 있다(forge에서 NLL 선택이 틀렸던
  경험). 최종 비교에는 둘 다 낸다.
- 출력: `log.jsonl`(단계별 학습·검증 손실), `run.json`(인자, 데이터 sha256, 단계 수). 기존 폴더는 덮어쓰지 않는다.
- 배치는 길이가 비슷한 예시를 묶어 패딩 포함 토큰 수(`--batch-tokens`, 기본 8192)로 제한한다.

### 확인한 것과 하지 않은 것 (2026-11-10)

- 단위 테스트(`tests/test_finetune.py`): 함수 부분집합의 중첩, 변형 유지, 라벨 마스크, 배치 예산, 패딩. 통과.
- Mac(MPS, bf16)에서 아주 작은 실행(함수 20개, 4단계)을 Qwen2.5-Coder-1.5B로 돌려 초기 검증 손실 계산, 학습 단계,
  로그가 도는 것을 확인했다. 단계당 약 110초(4천 토큰 두 묶음, 다른 작업이 CPU를 쓰는 중)라 **로컬 학습은 현실적이지
  않다. Colab GPU가 필요하다.** 저장(best/final)까지는 이 실행에서 확인하지 못했다(시간 제한으로 중단).
- **Qwen3.5(하이브리드)는 로컬에서 학습 단계를 끝내지 못했다.** 순전파는 된다(0.8B, 시퀀스 512에서 약 2초). 그러나
  `chunk_gated_delta_rule`과 `causal_conv1d`가 순수 PyTorch 대체 구현으로 돌아가고, 역전파 한 단계가 4분을 넘겼다.
  CUDA에서는 `flash-linear-attention`과 `causal-conv1d`를 깔면 빠른 커널이 쓰인다고 transformers가 안내하지만
  **설치와 속도는 Colab에서 확인한 값이 아직 없다.** 설치가 안 되면 Qwen3.5 두 후보의 학습 비용이 크게 늘 수 있다.
- LoRA 어댑터를 병합해 GGUF로 변환하고 양자화한 뒤의 정확도는 아직 재지 않았다.

### Colab 실행: `colab_run.py` (GPU를 쓰는 단계)

```bash
python3 training/colab_run.py --data <d0 폴더> --output <새 폴더> --session <이름> --plan probe --package-only   # GPU 없이 묶음만
python3 training/colab_run.py --data <d0 폴더> --output <새 폴더> --session <이름> --plan probe --gpu L4          # GPU 할당
```

로컬 `colab` CLI(이 컴퓨터에 이미 있는 인증)로 세션 하나를 만들고, 학습 스크립트와 D0의 train/val 파일(3.3MiB 압축)
만 올려 `colab_driver.py`가 설치 → 실행 → 결과 묶음을 처리한다. 예산 시간(`--budget-min`, 기본 60분)이 지나거나
오류가 나도 `finally`에서 세션을 멈춘다. 자격 증명은 올리지 않는다. 결과(`log.jsonl`, `run.json`, 어댑터, 실행별 로그,
`pip` 목록)는 내려받아 `--output` 아래에 푼다.

- `--plan probe`: 후보 3개를 각각 300함수 · 8단계로 돌려 **단계당 시간, 최대 메모리, 빠른 커널이 실제로 쓰였는지**만
  본다(`flash-linear-attention`을 설치하며, `--no-fla`로 느린 대체 구현도 잴 수 있다). 점수가 아니다.
- `--plan curve`: `--models` × `--sizes`(기본 1000,3000,all) 격자. probe 결과로 시간을 추정한 뒤에만 돌린다.
- 할당은 Colab 컴퓨팅 단위를 쓰므로 실행 전에 정한다.

### L4 probe 결과 (2026-11-14, `training/results/probe-l4-2026-11-14.json`)

세 번째 시도에서 세 후보 모두 끝까지 돌았다. 앞의 두 번은 실행 환경 문제로 실패했다.
1. Colab 이미지의 `torchao 0.10.0`을 `peft 0.21.2`가 거부했다. 지금은 설치 전에 제거한다.
2. 전체 시퀀스 logits(fp32, 어휘 15만~25만)가 묶음마다 5~7GiB를 써 메모리가 부족했다. 지금은 정답 위치에서만 출력층을
   계산한다. 두 구조 모두 전체 logits 손실과 같은 값인지 로컬에서 확인했다.

조건: L4, 300함수(524예시), 8단계, 단계 = 패딩 포함 8,192토큰 이하 묶음 4개, LoRA r=16, gradient checkpointing.

| 모델 | 단계당 시간(중앙값) | 최대 메모리 | 검증 손실 0 → 8단계 | 전체 6.7천 함수 2에폭 추정 |
|---|---:|---:|---|---:|
| Qwen2.5-Coder-1.5B | 19.9초 | 5.7GiB | 1.164 → 0.451 | 2.8시간 |
| Qwen3.5-0.8B-Base | 15.5초(11~19초, 첫 단계 78초) | 3.7GiB | 1.481 → 0.584 | 2.3시간 |
| Qwen3.5-2B-Base | 18.9초 | 6.3GiB | 1.351 → 0.541 | 2.8시간 |

- **Qwen3.5의 Gated DeltaNet은 `flash-linear-attention` 0.6.0 커널로 돌았다**(대체 구현 경고 없음). `causal_conv1d`는
  설치하지 않아 대체 구현으로 돌았다. 그래도 2B의 단계 시간은 Coder-1.5B와 비슷하다. 0.8B의 첫 단계 78초는
  Triton 커널 컴파일로 보인다(확인하지 않음).
- **검증 손실 값은 모델 비교에 쓰지 않는다.** 토크나이저가 달라 토큰당 손실을 직접 비교할 수 없고, 8단계는
  학습이라기보다 동작 확인이다.
- 처리량은 실제 토큰 기준 약 1.5천 tok/s다. PLAN_M2의 가정(3천)의 절반이다. 시간 추정 = 단계 수(예시 수에 비례해
  환산, 2에폭, 묶음 4개당 1단계) × 중앙값 단계 시간이다. 검증 손실 계산 시간은 넣지 않았다.
- **curve 격자 전체(모델 3개 × 1천/3천/전체, 시드 1개) 추정은 약 12~13시간(L4)이다.** 1천과 3천은 전체의 약 15%,
  45%로 셈했다. 메모리는 6GiB 안팎만 써서 여유가 크다. 따라서 gradient checkpointing을 끄거나 1에폭으로 줄이면
  시간이 줄어들 수 있다(측정하지 않음).

### 단축 설정 probe (2026-11-15, `training/results/probe-fast-l4-2026-11-15.json`)

gradient checkpointing을 끄고 같은 probe를 묶음 2가지(8,192토큰 × 4, 16,384토큰 × 2)로 돌렸다. **실행 6개 모두
첫 학습 단계에서 메모리가 부족했다**(L4 22GiB를 다 씀). 검증 손실 계산(역전파 없음)은 됐다.
checkpointing을 켜면 최대 메모리가 6GiB 안팎이므로, 차이는 거의 전부 역전파용 활성값이다. **L4에서 8천 토큰 묶음으로
학습하려면 checkpointing이 필요하다.** 더 작은 묶음(예: 4천 토큰 × 8)은 checkpointing 없이 들어갈 수도 있다.
다만 GPU 활용이 떨어져 실제로 빨라지는지는 재지 않았다.

## 이름 정확도 평가: `eval_names.py`

```bash
python3 training/eval_names.py --model Qwen/Qwen2.5-Coder-1.5B --adapter <out>/best --data <d0 폴더> \
    --out <새 폴더> --matrix <corpus matrix 폴더> [--functions N] [--batch 8]
```

토크나이저가 다르면 검증 손실을 비교할 수 없으므로, 모델 선정은 이 점수로 한다. 학습 때와 같은 프롬프트로 EOS까지
greedy 생성하고(상한 16 + 대상당 16토큰, 정답 길이는 쓰지 않음) 편집 목록 JSON을 읽어 대상 변수마다 채점한다.

- `exact`(대소문자 구분), `exact_ci`, `f1`(이름의 단어 단위, `eval/zeroshot_names.py`와 같은 정의), `missing`(편집
  목록에 없음; JSON을 읽지 못하면 그 예시의 대상 전부), `rejected`(`--matrix`가 있으면 원래 Fission 레코드에
  `apply_edits`를 돌려 적용기가 거부한 비율).
- **확신도 곡선:** 이름에 해당하는 생성 토큰의 로그 확률 합으로 대상을 정렬하고, 상위 100/80/60/40/20%의 정확도를
  낸다. 플러그인이 확신할 때만 이름을 바꾸게 할 때 얻는 정밀도다.
- 가림(`FUN_<주소>`)과 가리지 않음, 최적화 수준, 매개변수/지역변수별로 나눠 낸다. 기본은 val 전체(함수 715개,
  예시 2,439개)이고 test는 읽지 않는다. val은 isl 안의 분할이라 같은 데이터로 학습한 모델끼리 비교하는 용도다.
- 출력: `summary.json`, 대상별 `targets.jsonl`, 생성 원문 `generations.jsonl`.

확인한 것(2026-11-15, Mac MPS, probe 어댑터 = 8단계만 학습, val 함수 10개 = 예시 32개 · 대상 110개):

| 어댑터 | exact | f1 | missing | rejected | 예시당 시간(배치 1 / 4) |
|---|---:|---:|---:|---:|---:|
| Coder-1.5B probe | 22.7% | 27.6% | 1.8% | 10.0% | 1.1초 / 1.0초 |
| Qwen3.5-0.8B probe | 11.8% | 13.6% | 0.9% | 20.0% | 1.7초 / 1.5초 |

- 8단계 어댑터라 점수 자체는 의미가 없다. 파이프라인이 돈다는 확인이다. JSON 파싱 실패는 없었다.
- 거부된 이름은 대부분 코드에 이미 있는 식별자(`local_20`, `x8`)나 중복 이름이었다. 적용기 검사가 실제로 걸러 낸다.
- **배치 1과 4의 생성은 32개 중 1개만 달랐다**(두 모델 모두, bf16에서 확률이 거의 같은 지점). Qwen3.5의 Gated
  DeltaNet에서도 왼쪽 패딩이 결과를 바꾸지 않는다. 점수는 0.8B는 같았고 Coder는 대상 1개 차이였다.
- 로컬 속도로 val 전체는 모델당 약 40~90분이다(2B는 재지 않음). GPU 없이 돌릴 수 있다.

## 모델 선정 (2026-11-15, `training/results/select-l4-2026-11-15.json`)

세 후보를 같은 3천 함수(예시 5,198개, 시드 1, 2에폭, checkpointing 켬)로 L4에서 학습했다(세션 1개, 약 3.8시간).
그다음 val 전체(함수 715개, 예시 2,439개, 대상 변수 8,165개)를 Mac에서 `eval_names.py`로 평가했다.

| 모델 | 학습(단계, 시간, 최대 메모리) | exact 전체 | 가리지 않음 | 가림 | f1 | 상위 60% / 40% 정확도 | 적용기 거부 |
|---|---|---:|---:|---:|---:|---:|---:|
| Qwen2.5-Coder-1.5B | 198, 74분, 5.7GiB | **63.2%** | 66.7% | 59.8% | 64.6% | 84.1% / 91.7% | 0.11% |
| Qwen3.5-2B-Base | 218, 81분, 7.4GiB | 62.8% | 66.1% | 59.5% | 64.4% | 82.9% / 89.7% | 0.11% |
| Qwen3.5-0.8B-Base | 218, 53분, 4.8GiB | 58.2% | 62.1% | 54.3% | 59.8% | 79.1% / 87.3% | 0.23% |

쌍체 부트스트랩(D0 그룹 = 템플릿 복제 묶음 420개 단위로 1,000번 재표집, exact 차이의 95% 구간):

| 비교 | 전체 | 가리지 않음 | 가림 |
|---|---|---|---|
| Coder − 2B | +0.5점 [−1.4, +2.4] | +0.7 [−2.1, +3.2] | +0.3 [−1.6, +2.1] |
| Coder − 0.8B | +5.0 [+2.6, +7.4] | +4.7 [+2.1, +7.1] | +5.4 [+2.2, +8.8] |
| 2B − 0.8B | +4.5 [+2.3, +6.8] | +4.0 [+1.9, +5.9] | +5.1 [+2.1, +8.3] |

- **0.8B는 다른 두 후보보다 약 5점 낮고, 구간이 0을 포함하지 않는다.** 후보에서 뺀다.
- **Coder-1.5B와 2B는 이 데이터로 구별되지 않는다**(차이 0.5점, 구간 ±2점). 둘이 함께 맞힌 대상은 55%, 둘 중
  하나라도 맞힌 대상은 71%라 틀리는 대상이 꽤 다르다.
- 동률일 때의 근거는 Coder-1.5B 쪽이다. Q4_K_M이 0.99GB로 2B의 1.31GB보다 작고, Metal 생성은 162 tok/s로
  2B의 115 tok/s보다 빠르다(G1, 베이스 모델). 토큰도 약 10% 적게 쓴다. Mac MPS 평가 시간도 20분 대 49분이었다
  (PyTorch MPS에서 Gated DeltaNet은 대체 구현이라 llama.cpp 속도를 대신하지 못한다). 확신도 상위 40%의 정확도도
  Coder가 2점 높지만, 이 차이의 구간은 재지 않았다.
- 한계: 시드 1개다. val은 isl 안의 분할이라 이름 관습이 학습과 겹치므로 일반화 근거가 아니다. 63%라는 값을
  학습 전 3-shot의 11.5%(`eval/README.md`)와 직접 비교하면 안 된다. 세트, 대상 선정, 입력 형식이 다르다.
  best와 final이 같은 어댑터다(검증 손실이 마지막 단계까지 내려감). 그래서 2에폭이 짧았을 수 있다.
  xproj(capstone)와 test는 쓰지 않았다.
- JSON 파싱 실패는 2,439개 중 0.8B의 1개뿐이었다. 적용기 거부는 0.1~0.2%였다.

### Coder-1.5B 곡선 1차 실행 (2026-11-16, 결과 손실)

L4 세션 `ft-curve-coder-1`에서 1천 함수와 전체(6,669) 함수를 시드 1로 학습했다. 두 실행 모두 끝까지 돌았다
(약 3.5시간). 그러나 **이 Mac의 디스크가 가득 차(남은 공간 0.3GiB) 결과 묶음을 내려받지 못했다.** 실행기는 실패 직후
세션을 멈췄고, 그때 VM에만 있던 어댑터가 함께 사라졌다. 남은 것은 상태 polling에 찍힌 검증 손실뿐이다(600예시
고정 부분집합, 점수 아님).

| 학습 함수 | 단계 | 학습 시간 | 검증 손실(best = 마지막 평가) |
|---:|---:|---:|---:|
| 1,000 | 68 | 27분 | 0.2296 |
| 3,000 (모델 선정 실행) | 198 | 74분 | 0.1589 |
| 6,669 (전체) | 443 | 2.8시간 | 0.1311 |

검증 손실은 전체까지 계속 내려갔다. 이름 정확도로 확인하려면 다시 실행해야 한다. 실행기는 이제 할당 전에
로컬 여유 공간을 확인하고(`--min-free-gb`, 기본 5), 다운로드가 실패하면 세션을 유지한 채 1분마다 다시
시도한다(`--download-grace-min`, 기본 60분).
